# 10 · PAPERCLIP — what Scout should reuse

Research date: **2026-10-02**. Scope: the official `paperclipai/paperclip` repository, its implementation and first-party provider documentation. Source snapshot: [`c46e41e81c03cd3c8b64cf993615b604d7fe8c62`](https://github.com/paperclipai/paperclip/commit/c46e41e81c03cd3c8b64cf993615b604d7fe8c62), committed 2026-10-02. This is a source review, **not a successful live Paperclip/provider run**. Nothing was installed, upgraded, signed in, or connected.

## Recommendation

**Keep Scout as the person's working surface and markdown source of truth. Reuse Paperclip's orchestration contracts; consider an optional worker bridge later.** Paperclip is a substantial agent control plane, useful for assigning independent AI workers, recovering interrupted work, tracing goals, and governing tools. It does not supply Scout's human time log, one-Now-item conductor, approval-curated learning, or markdown collections.

Replacing Scout with Paperclip would conflict with `GOAL.md`: Paperclip owns an Express server and relational database, while Scout requires files as truth and excludes server-dependent infrastructure from v1. Paperclip's current package requires **Node ≥24.11.0**; using it beside Scout (currently declaring Node ≥22) entails an explicit runtime choice. Its MIT license allows reuse with the required copyright/license notice. Sources: [database architecture](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/doc/DATABASE.md), [package engines](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/package.json#L103), [license](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/LICENSE).

This recommendation is an architectural inference from those constraints, not a claim that an integration has been implemented.

## What actually exists

| Scout requirement | Evidence in current Paperclip | Consequence for Scout |
|---|---|---|
| Goal-directed workers | Issues link to projects, goals and parent issues. The heartbeat protocol asks workers to read ancestry, claim work and leave durable progress. | Reuse goal ancestry and explicit next-action receipts in Scout's existing tasks/dispatch modules. |
| Parallel work without duplicate claims | Issue checkout is a server operation; another owner produces a conflict. Child issues let a parent wake on completion. | Keep Scout's atomic task claiming; adopt child completion events instead of polling subagents. |
| Wake-up and recovery | A persisted heartbeat queue, adapter sessions, lifecycle gates, and bounded semantic continuations exist in source. | A small persisted Scout run state can copy the contract without copying a second scheduler or datastore. |
| Scheduled reviews | Routines support timezone-aware cron, manual/API/webhook triggers, idempotency keys, coalescing and bounded catch-up. | Scout already has its local scheduler. Apply these idempotency/concurrency ideas there. |
| Ongoing agent conversation | Experimental Agent Chat is task-backed, per company/agent/user. Ordered messages, session resets and idle-versus-active state exist. | Useful model for a conductor conversation that delegates execution into ordinary tasks. |
| Approvals | Hiring/strategy approvals, issue interactions, execution policies and connection tool-action reviews exist. | Preserve Scout's pipeline gate; an external approval does not itself authorize a Scout write, publication or payment. |
| Cost limits | Budget policies sum recorded billed cents, warn, pause scopes and cancel work. | Monetary budgets help API use. Separate them from subscription quotas and from human work minutes. |
| Curated knowledge | Sessions, issue history, instructions and external memory connections exist. A general memory service is described in a design plan. | Scout's evidence, decay, correction, territory yield and approved learnings remain its own product advantage. |

Implementation sources: [heartbeat protocol](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/docs/guides/agent-developer/heartbeat-protocol.md), [heartbeat service](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/heartbeat.ts), [routines API](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/docs/api/routines.md), [routines service](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/routines.ts), [approval service](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/approvals.ts), [issue interactions](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/issue-thread-interactions.ts), [budget service](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/budgets.ts).

### Chat has real implementation, with an explicit maturity limit

`enableAgentChat` is experimental and defaults to false. Conversation containers are issues unique to company, agent and user. A successful reply settles the turn without completing the conversation. Idle conversations are excluded from normal execution counts; substantial execution is handed to linked ordinary tasks. This is a good conceptual fit for Scout's continuous conductor plus separate workers. It is not a drop-in replacement for Scout's daily chat or human work timer. Older top-level specification text says communication is tasks/comments only; the newer Agent Chat section and code must be read together. Sources: [Agent Chat implementation contract](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/doc/SPEC-implementation.md#L1678), [issues service](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/issues.ts).

### The memory roadmap is not Scout's completed learning loop

The memory landscape and service proposal describe provider bindings, provenance, hooks, search, correction and costs. They are plans, not proof that this complete generic service is shipped. Current source includes a catalog of external memory connectors, but no corresponding `memory_bindings`/`memory_operations` schema or general memory service was found in the reviewed paths. Session continuation also does not prove a worker avoids rediscovering known territory after a week. Scout must retain its tested hot cache, stale-claim exclusion, rejection reasons and human approval of new learnings. Sources: [memory landscape](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/doc/memory-landscape.md), [memory service proposal](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/doc/plans/2026-03-17-memory-service-surface-api.md), [connector catalog](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/packages/shared/src/memory-connectors.ts).

## Providers, subscriptions and actual permission boundaries

Paperclip runs the provider's existing agent runtime. It does not repair an account's authentication, add model entitlement, or increase its quota.

| Runtime | Current Paperclip implementation | What is still required |
|---|---|---|
| Claude Code | Built-in adapter; persisted sessions, environment probes, API/token/subscription auth paths and quota handling. | Working Claude CLI authentication and available quota. Its documented default permission bypass is unsuitable for Scout's text-only brain. |
| Codex | Built-in adapter; session handling, per-agent managed homes, explicit API key versus host subscription auth precedence, environment tests. | Working Codex authentication and an account-supported model. Copying configuration must not accidentally change billing mode or share rotating credentials across a fleet. |
| Gemini CLI | Package, built-in registry entry and shared type enum all include `gemini_local`. | Working local authentication/API key and eligible model. The overview still calls the package experimental and absent from the stable enum; that sentence disagrees with the pinned code. |
| Devin CLI | No dedicated built-in Devin adapter was found. Generic process/HTTP adapters and external adapter loading exist. | A custom adapter would need output/session/usage parsing, quota handling, tool policy and cancellation semantics. A process wrapper alone does not establish those contracts. |

**Read-only is not text-only.** Scout's Today brain claims to receive only prompt data. The CLI invocation must actually remove tool access rather than merely restrict write approval:

| CLI | Verified first-party behavior | Appropriate text-only constraint |
|---|---|---|
| Gemini | `--approval-mode plan` permits filesystem reads, search/web tools, research subagents and interaction tools. `--allowed-tools` bypasses approval; it does not remove unlisted tools. | `tools.core: []` can remove built-ins, but Gemini 0.46's remaining context/auth isolation is not established. Keep Today disabled: an isolated `GEMINI_CLI_HOME` loses existing OAuth unless credentials are copied, which this task does not authorize. |
| Devin | `--permission-mode auto` is an alias for `normal`; reads/search auto-approve, while writes/shell prompt. `/ask` and `/plan` retain read tools. | `disabled_tools` is documented for explicit names, but no universal no-tools flag/empty allowlist was verified. Deny rules are useful containment, not proof of an empty tool inventory. Keep text-only Devin disabled until the installed runtime's complete tool set and isolation can be demonstrated. |
| Claude | `--tools ""` removes built-ins, **not MCP tools**. `--allowedTools` concerns approval. | Today uses print mode, `--tools ""`, `--disallowedTools "*"`, strict empty MCP, empty setting sources, `--safe-mode`, disabled hooks/skills/Chrome and no session persistence, from an empty temporary directory. Auth is retained; organization-managed policy still applies. |
| Codex | `codex exec --sandbox read-only` restricts model-generated shell command writes; it does not disable tools or file reads. `-c` provides per-run configuration overrides. | No documented universal CLI no-tools switch was verified. Do not call this text-only solely because it runs in a read-only sandbox. Retain disabled status for that contract until exact installed-version tool settings are established and tested. |

These are documentation/source findings, not an executed adversarial test against the installed CLIs. Provider versions can differ; unsupported policy must fail closed.

**Installed Gemini 0.46 verification.** `GEMINI_CLI_SYSTEM_SETTINGS_PATH` selects a system override file, merged after user/workspace settings. However, `LoadedSettings.computeMergedSettings` rebuilds `admin` from defaults and remote admin controls, ignoring file-based admin values: putting `admin.mcp.enabled=false` and `admin.extensions.enabled=false` in that file is ineffective. The hook switch is `hooksConfig.enabled`, not `hooks.enabled`. `setGeminiMdFilename` adds requested filenames to the existing default, so `context.fileName=[]` retains `GEMINI.md`, including global context. These findings match the installed bundle and pinned official source. Sources: [v0.46 settings merge](https://github.com/google-gemini/gemini-cli/blob/v0.46.0/packages/cli/src/config/settings.ts), [v0.46 context filenames](https://github.com/google-gemini/gemini-cli/blob/v0.46.0/packages/core/src/tools/memoryTool.ts), [hook configuration](https://geminicli.com/docs/reference/configuration/).

Claude's `--safe-mode` preserves authentication while suppressing customizations, but administrator policy hooks remain active, and session-level `disableAllHooks` cannot override them. A managed installation needs a policy audit/runtime boundary before claiming complete isolation. `--bare` is unsuitable for retaining this machine's subscription OAuth: installed help explicitly limits its Anthropic auth to API key/helper. Sources: [safe-mode and CLI flags](https://code.claude.com/docs/en/cli-reference), [managed hook precedence](https://code.claude.com/docs/en/hooks#disable-or-remove-hooks).

**Scout implementation in this task.** `agentProviders.mjs` now has a separate `textOnly` descriptor; interactive assistant argv remains independent. Gemini, Devin and Codex fail closed for Today. Claude requires installed help to expose every mandatory restriction before eligibility. `brain.mjs` persists a reservation before invoking each provider and records completion separately. Daily limits default to **40 light attempts and 4 heavy attempts**; failed and unfinished attempts count, and Claude fallback always spends the heavy cap. Concurrent calls share the synchronous event-log reservation gate; this governs one Scout backend, not multiple independent servers writing the same vault. Regression tests cover concurrent saturation, failure, restart/orphan receipts, fallback billing tier, old dates, high log volume and workspace switches. No real model response was obtained as part of this verification.

### Monetary budgets cannot protect every subscription limit

The budget service enforces sums of `costEvents.costCents` for company/agent/project scopes, with monthly UTC or lifetime windows. The heartbeat ledger distinguishes unknown/unpriced receipts from reported prices and normalizes subscription-included usage to zero incremental billed cents. Therefore a subscription worker can consume substantial quota without approaching a billed-dollar cap. Budget enforcement depends on recorded usage; concurrent/in-flight calls can consume resources before the stop is observed. Add run count, concurrency, timeout and quota cooldown limits separately. Sources: [budget aggregation](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/budgets.ts#L135), [ledger normalization](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/heartbeat.ts#L5296), [README budget limitation](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/README.md).

An account-specific Gemini rejection does not prove free personal access disappeared for everyone: current Google documentation still describes free Google-account access and a limited unpaid API-key Flash tier. This does not establish this user's eligibility. Likewise, Devin's description of SWE as inexpensive is not proof it is free or included in another provider's subscription. Sources: [Gemini quota/auth tiers](https://geminicli.com/docs/resources/quota-and-pricing/), [Devin model guidance](https://docs.devin.ai/cli/models).

## Worker-scoped access and finance isolation

Paperclip has real company-scoped authorization, principal grants and responsible-user intersection. Its authorization service checks an agent decision against the current responsible user's permissions for applicable actions; this includes exceptions and an explicit shadow-mode path, so it is not an unconditional blanket guarantee for every call. Sources: [authorization implementation](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/authorization.ts#L2355), [responsible-user tests](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/__tests__/heartbeat-responsible-user-invariant.test.ts).

Its low-trust preset narrows issue/project/root-task scope, tool classes, secret bindings and delegation. Managed low-trust work requires a sandbox environment and isolated workspace and fails closed without them. The documentation explicitly distinguishes this containment from general human/project privacy. A local process can still access whatever its operating-system identity permits. A VA's assistant must therefore never receive finance files, secrets or privileged tool credentials in its runtime merely because an API route hides them. Sources: [low-trust contract](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/doc/LOW-TRUST-PRESETS.md), [runtime containment code](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/server/src/services/low-trust-runtime-containment.ts).

For Scout, reuse the principal-intersection idea across cache rendering, searches, task assignment, records and hub bundles. OpsGraph universes should stay separate physical access boundaries for restricted material until worker-scoped read permissions are implemented and demonstrated. Ordinary tags/collections are organization, not authorization.

## Smallest useful bridge, if later needed

Keep two clear owners: Scout owns records, human work events, decisions and curated memory; optional Paperclip owns only external worker issue/run state. A bridge would:

1. Export an already-approved Scout task with stable Scout ID, goal ancestry, a filtered hot-cache snapshot, permitted actions and an idempotency key.
2. Let one worker claim it; persist the Paperclip issue/run IDs on a bridge receipt, not a duplicate editable backlog.
3. Import artifacts through `_inbox/` or Scout's existing upsert/proposal APIs. Preserve source/run provenance and let Scout's gate decide their effect.
4. Translate completion, blocked, approval-needed and quota-failure events into Scout Activity/Needs you and wake the conductor once.
5. Cancel/pause delegated work from Scout; do not let two schedulers independently dispatch the same task or two systems promote the same memory.

A localhost authenticated HTTP bridge is the smallest demonstrable option. Do not embed the whole Paperclip UI, migrate markdown into its database, mount the entire OpsGraph tree, or import its broad CLI permission defaults. Current Paperclip also sends opt-out first-party usage telemetry; a later self-hosted trial should make the local-first user's telemetry choice explicit. Source: [telemetry documentation](https://github.com/paperclipai/paperclip/blob/c46e41e81c03cd3c8b64cf993615b604d7fe8c62/README.md#L538).

## Prioritized Scout gaps

1. **P0 — prove one real provider can answer under the advertised permission contract.** Track installed version, real model ID, auth/billing mode and failure reason; a CLI binary or login file is not readiness. Prove tools are unavailable before sending workspace context. Keep light-to-heavy fallback an explicit setting.
2. **P0 — connect the human day to the actual goal.** The existing Today loop schedules work and measures minutes. Add goal ancestry, measurable outcomes and a concrete next action to worker tasks; daily/weekly reviews should compare outcomes against goals rather than equate activity with progress.
3. **P1 — one durable worker lifecycle.** Reuse existing dispatch/tasks/log modules for claim → run → blocked/needs-you/completed, cancellation, crash recovery, bounded retries and child completion wakes. Do not create another orchestration subsystem.
4. **P1 — preserve learning proof.** An approved review learning must affect a subsequent cache/plan; test rejection evidence, stale exclusion and a run one week later that starts with known territory.
5. **P1 — enforce worker access in code.** Principal scope must bound reads, writes, cache/hub material and tool credentials. Finance isolation requires runtime/file separation as well as API checks.
6. **P2 — provider quota and efficiency controls.** Daily attempt caps and durable receipts were added in this task. Per-purpose concurrency, model-turn limits and quota cooldown/reset handling remain. Billed-dollar limits alone cannot govern subscriptions.
7. **P2 — bridge only when it earns its infrastructure cost.** Demonstrate a bounded worker task and import its result through Scout's existing pipeline before adopting a second server/database.

Acceptance proof for reuse: two workers cannot complete the same claim; a duplicated scheduled wake creates one review; a blocked worker yields one actionable decision; a rejected output cannot change canonical records; a revoked scope removes subsequent read access; provider exhaustion pauses dependent work without silently billing another account. These are proposed Scout checks, not claims that they have all passed.
